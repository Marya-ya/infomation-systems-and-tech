

## Введение

Учетные записи являются фундаментом современных информационных систем. Они обеспечивают управление доступом пользователей к ресурсам, хранение персональных данных, отслеживание действий и реализацию политик безопасности. Без системы управления учетными записями невозможно представить ни одну современную операционную систему, облачный сервис, корпоративную сеть или веб-приложение.

Система идентификации пользователя – это комплекс технических и организационных средств, предназначенный для распознавания, проверки подлинности и управления доступом пользователей к информационным ресурсам.

---

## Понятие учетной записи

### Определение

**Учетная запись** – это набор данных и параметров, которые система использует для:
- Определения и распознавания пользователя
- Хранения его персональных данных
- Управления правами доступа
- Отслеживания действий и активности

Учетная запись служит идентификационным профилем пользователя в системе. Она может быть создана:
- При регистрации на веб-сайте
- При добавлении пользователя в корпоративную сеть
- При установке операционной системы
- При подключении к облачному сервису

### Назначение учетной записи

Учетная запись выполняет несколько критически важных функций:

| Функция | Описание |
|---------|----------|
| **Идентификация** | Система определяет, кто перед ней: владелец устройства, сотрудник компании или внешний пользователь |
| **Персонализация** | Каждый пользователь может сохранять личные файлы, настройки интерфейса и предпочтения |
| **Контроль доступа** | Система ограничивает доступ к ресурсам в соответствии с правами пользователя |
| **Аудит и мониторинг** | Система ведет журналы действий пользователя для анализа, контроля и безопасности |
| **Управление ресурсами** | Распределение системных ресурсов, квот дискового пространства и вычислительных мощностей |

## Элементы и компоненты учетной записи

### 1. Основные идентификационные данные

#### Логин (имя пользователя)
Уникальный идентификатор, который система использует для распознавания пользователя. Логин может быть представлен:
- Текстовым именем (например, `ivan_ivanov`)
- Email-адресом (например, `user@company.com`)
- Номером телефона (например, `+79991234567`)
- Уникальным ID или токеном (например, UUID)

**Пример:** Когда пользователь входит в систему, он первым делом вводит логин – это процесс идентификации.

#### UID (User ID)
Уникальный числовой идентификатор в системе, присвоенный при создании учетной записи. В операционных системах Linux/Unix каждому пользователю присвоен уникальный UID.

**Пример:**
```
Пользователь: anna_petrov
UID: 1003
GID (Group ID): 1000
```

### 2. Аутентификационные данные

#### Пароль
Главный инструмент защиты учетной записи. Пароль предотвращает несанкционированный доступ и должен:
- Быть достаточно сложным (содержать прописные, строчные буквы, цифры, специальные символы)
- Храниться в защищенном виде (хешированный или зашифрованный)
- Регулярно изменяться
- Не разглашаться третьим лицам

**Пример хеширования пароля:**
```
Исходный пароль: MySecurePass123!
Хеш SHA-256: 4a7b3c2f9e1d8a5b6c9d0e1f2a3b4c5d6e7f8a9b
```

#### Дополнительные факторы аутентификации
- **Биометрические данные**: отпечатки пальцев, распознавание лица, сканирование сетчатки
- **Токены и ключи**: USB-ключи, аппаратные токены, цифровые сертификаты
- **Временные коды**: OTP (One-Time Password), коды из SMS, приложения-генераторы кодов
- **Вопросы безопасности**: ответы на предварительно установленные вопросы
- **Биометрия поведения**: анализ паттернов использования, скорость печати

### 3. Данные о правах доступа

#### Роли пользователя
Совокупность прав, которые определяют возможные действия пользователя в системе.

**Примеры ролей:**
```
Пример 1: Веб-приложение для управления проектами
- Администратор: полный доступ ко всем функциям
- Менеджер проекта: создание, редактирование проектов
- Разработчик: просмотр, редактирование задач
- Гость: только просмотр информации

```

#### Привилегии
Конкретные разрешения на выполнение определенных действий.

| Привилегия | Описание |
|-----------|----------|
| `read` | Чтение файлов и данных |
| `write` | Создание и редактирование файлов |
| `execute` | Запуск программ и скриптов |
| `delete` | Удаление файлов |
| `share` | Совместный доступ к ресурсам |
| `admin` | Административные функции |

### 5. Метаданные учетной записи

- **Дата создания**: когда была создана учетная запись
- **Дата последнего входа**: последний момент входа пользователя
- **Статус активности**: активна ли учетная запись или заблокирована
- **Дата истечения**: когда истекает действие учетной записи (для временных учетных записей)
- **Количество попыток входа**: неудачные попытки входа (для обнаружения атак)
- **Состояние пароля**: нужна ли смена пароля, истек ли срок пароля

## Система идентификации пользователя

### Определение и уровни идентификации

**Идентификация** – это процесс распознавания пользователя по его уникальному идентификатору и получение информации о его принадлежности к системе.

Идентификация бывает двух типов:

#### 1. Первичная идентификация
Проводится при регистрации нового пользователя в системе. На этом этапе:
- Пользователь предоставляет личные данные
- Системе присваивается уникальный идентификатор
- Создается учетная запись в базе данных
- Информация регистрируется в реестре системы

**Пример:**
```
Новый пользователь заполняет форму регистрации на сайте:
- Email: user@example.com
- ФИО: Иван Иванов
- Дата рождения: 15.01.1990

Система создает запись:
- UID: 5432
- Логин: ivan_ivanov
- Email: user@example.com
- Статус: Активна
- Дата создания: 24.12.2025
```

#### 2. Вторичная идентификация
Проводится при каждом последующем входе в систему:
- Пользователь предоставляет идентификатор (логин или email)
- Система ищет соответствующую запись в базе данных
- Проверяется наличие и статус учетной записи
- Инициируется процесс аутентификации

**Пример:**
```
Пользователь вводит логин: ivan_ivanov

Система выполняет поиск:
1. Проверяет наличие учетной записи с логином "ivan_ivanov"
2. Находит UID: 5432
3. Проверяет, активна ли учетная запись (Статус: Активна)
4. Переходит к аутентификации
```

## Процессы управления доступом

### 1. Идентификация (Who are you?)
**Вопрос:** "Кто ты?"
**Задача:** Определить идентификацию пользователя
**Способ:** Предъявление уникального идентификатора (логин, email, ID)
**Результат:** Система узнает, кто обращается к ней

### 2. Аутентификация (Prove it!)
**Вопрос:** "Докажи, что ты именно тот, кто говоришь?"
**Задача:** Подтвердить подлинность пользователя
**Способ:** Предъявление доказательств подлинности (пароль, биометрия, токен)
**Результат:** Система подтверждает, что это именно нужный пользователь

**Схема аутентификации:**

```
ОДНОФАКТОРНАЯ АУТЕНТИФИКАЦИЯ
┌─────────────────────────────────┐
│ Что ты знаешь?                  │
├─────────────────────────────────┤
│ • Пароль                        │
│ • PIN-код                       │
│ • Ответ на секретный вопрос     │
└─────────────────────────────────┘

ДВУХФАКТОРНАЯ АУТЕНТИФИКАЦИЯ
┌─────────────────────────────────┐
│ Что ты знаешь?                  │
│ + Что ты имеешь?                │
├─────────────────────────────────┤
│ • Пароль + SMS-код              │
│ • Пароль + аппаратный токен     │
│ • Пароль + мобильное приложение │
└─────────────────────────────────┘

ТРЕХФАКТОРНАЯ АУТЕНТИФИКАЦИЯ
┌─────────────────────────────────┐
│ Что ты знаешь?                  │
│ + Что ты имеешь?                │
│ + Кто ты есть?                  │
├─────────────────────────────────┤
│ • Пароль + токен + отпечаток    │
│ • Пароль + USB-ключ + лицо      │
│ • PIN + карта + биометрия       │
└─────────────────────────────────┘
```

**Пример двухфакторной аутентификации:**

```
Этап 1: Ввод пароля
├─ Пользователь: Вводит логин "anna_petrov" и пароль
└─ Система: Проверяет пароль в базе данных

Этап 2: Отправка кода подтверждения
├─ Система: Отправляет 6-значный код на номер +79991234567
└─ Пользователь: Получает SMS с кодом: 456789

Этап 3: Ввод кода подтверждения
├─ Пользователь: Вводит код 456789
└─ Система: Проверяет код (совпадает!)

Результат: Доступ предоставлен! ✓
```

### 3. Авторизация (What can you do?)
**Вопрос:** "Что ты можешь делать в этой системе?"
**Задача:** Определить права и разрешения пользователя
**Способ:** Проверка ролей, привилегий и политик доступа
**Результат:** Система предоставляет доступ к определенным ресурсам и функциям

**Пример авторизации в интернет-магазине:**

```
┌──────────────────────────────────────┐
│ РОЛЬ: АДМИНИСТРАТОР                  │
├──────────────────────────────────────┤
│ ✓ Просмотр заказов (свои и других)   │
│ ✓ Создание новых товаров             │
│ ✓ Редактирование товаров             │
│ ✓ Удаление товаров                   │
│ ✓ Управление пользователями          │
│ ✓ Просмотр статистики                │
│ ✓ Изменение цен                      │
└──────────────────────────────────────┘

┌──────────────────────────────────────┐
│ РОЛЬ: ПОКУПАТЕЛЬ                     │
├──────────────────────────────────────┤
│ ✓ Просмотр товаров                   │
│ ✓ Просмотр своих заказов             │
│ ✓ Редактирование своего профиля      │
│ ✓ Оставление отзывов                 │
│ ✗ Создание товаров                   │
│ ✗ Удаление товаров                   │
│ ✗ Просмотр заказов других            │
│ ✗ Управление ценами                  │
└──────────────────────────────────────┘
```

### Модели управления доступом

#### 1. RBAC (Role-Based Access Control) – Управление доступом на основе ролей

```
Структура RBAC:
┌──────────────┐
│ ПОЛЬЗОВАТЕЛЬ │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│    РОЛЬ      │ (Администратор, Менеджер, Пользователь)
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ ПРИВИЛЕГИИ   │ (read, write, delete, execute)
└──────┬───────┘
       │
       ▼
┌──────────────┐
│  РЕСУРСЫ     │ (Файлы, базы данных, приложения)
└──────────────┘

Пример:
Пользователь: Мария Сидорова
├─ Роль: Менеджер проекта
│  ├─ Привилегия: read (Просмотр всех документов проекта)
│  ├─ Привилегия: write (Создание и редактирование задач)
│  ├─ Привилегия: delete (Удаление завершенных задач)
│  └─ Ресурсы: Проект "Веб-платформа"
│
└─ Роль: Разработчик
   ├─ Привилегия: read (Просмотр кода)
   ├─ Привилегия: write (Редактирование кода)
   └─ Ресурсы: Git репозиторий
```

#### 2. ABAC (Attribute-Based Access Control) – Управление доступом на основе атрибутов

```
Атрибуты доступа:
┌──────────────────────────────────┐
│ АТРИБУТЫ ПОЛЬЗОВАТЕЛЯ            │
├──────────────────────────────────┤
│ • Должность: Менеджер            │
│ • Отдел: Маркетинг               │
│ • Уровень безопасности: Secret   │
│ • Локация: Москва                │
│ • Часовой пояс: UTC+3            │
└──────────────────────────────────┘

┌──────────────────────────────────┐
│ АТРИБУТЫ РЕСУРСА                 │
├──────────────────────────────────┤
│ • Тип: Финансовые данные         │
│ • Классификация: Confidential     │
│ • Отдел-владелец: Бухгалтерия    │
│ • Время доступа: 09:00-17:00     │
└──────────────────────────────────┘

┌──────────────────────────────────┐
│ ПРАВИЛА ДОСТУПА                  │
├──────────────────────────────────┤
│ IF (пользователь.отдел =         │
│     ресурс.отдел-владелец)       │
│ AND (пользователь.уровень >=     │
│      ресурс.классификация)       │
│ THEN Доступ разрешен             │
│ ELSE Доступ запрещен             │
└──────────────────────────────────┘
```

#### 3. Избирательный контроль доступа (DAC)

```
Владелец ресурса самостоятельно устанавливает права доступа.

Пример - Матрица доступа:
┌──────────┬──────────┬────────┬─────────┐
│ Учетная  │ Файл 1   │ Файл 2 │ Файл 3  │
│ запись   │ (отчет)  │ (код)  │ (ресурс)│
├──────────┼──────────┼────────┼─────────┤
│ Иван     │ rwx      │ r      │ ---     │
│ Мария    │ rw       │ rwx    │ r       │
│ Петр     │ ---      │ rx     │ rwx     │
└──────────┴──────────┴────────┴─────────┘

r = read (чтение)
w = write (запись)
x = execute (исполнение)
- = нет доступа
```

#### 4. Мандатный контроль доступа (MAC)

```
Система управления определяет права доступа по уровням классификации.

Иерархия уровней секретности:
┌─────────────────────────────┐
│ TOP SECRET (Совершенно      │
│ секретно) - Уровень 4       │ ← Доступ только для президента
├─────────────────────────────┤
│ SECRET (Секретно)           │ ← Доступ для топ-менеджеров
│ - Уровень 3                 │
├─────────────────────────────┤
│ CONFIDENTIAL (Конфиденц.)   │ ← Доступ для менеджеров
│ - Уровень 2                 │
├─────────────────────────────┤
│ PUBLIC (Открытая)           │ ← Доступ для всех
│ - Уровень 1                 │
└─────────────────────────────┘

Правило "No Read Up" (не читать выше):
Пользователь уровня 2 НЕ может читать данные уровня 3 и 4

Правило "No Write Down" (не писать ниже):
Пользователь уровня 3 НЕ может писать данные уровня 1 и 2
```

### Пример 1: Корпоративная сеть

```
СЦЕНАРИЙ: Сотрудник входит в корпоративную сеть

1. ИДЕНТИФИКАЦИЯ
   ├─ Сотрудник вводит логин: mikhail.petrov
   └─ Система находит учетную запись в Active Directory

2. АУТЕНТИФИКАЦИЯ
   ├─ Сотрудник вводит пароль: ########
   ├─ Система проверяет пароль (совпадает)
   ├─ Система отправляет код на приложение Microsoft Authenticator
   └─ Сотрудник одобряет вход в приложении

3. АВТОРИЗАЦИЯ
   ├─ Система проверяет роли пользователя:
   │  ├─ Группа: "Разработчики"
   │  ├─ Группа: "Проект-А"
   │  └─ Группа: "VPN-доступ"
   │
   ├─ Система предоставляет доступ к:
   │  ├─ Сетевым папкам отдела (/shared/dev)
   │  ├─ Репозиторию кода (GitHub Enterprise)
   │  ├─ Системе управления задачами (Jira)
   │  ├─ Email-серверу
   │  └─ VPN для удаленного доступа

РЕЗУЛЬТАТ: Пользователь успешно вошел в корпоративную сеть ✓
Он может работать с разрешенными ресурсами, но не может:
- Удалять пользователей (только администратор)
- Менять политики безопасности (только администратор)
- Получать доступ к финансовым документам (другой отдел)
```

### Пример 2: Облачное хранилище

```
СЦЕНАРИЙ: Пользователь входит в облачное хранилище (Google Drive)

1. ИДЕНТИФИКАЦИЯ

РЕЗУЛЬТАТ: Пользователь видит:

```

## Безопасность учетных записей

### Основные угрозы и риски

```
┌─────────────────────────────────────────────────────┐
│           УГРОЗЫ БЕЗОПАСНОСТИ                       │
└─────────────────────────────────────────────────────┘

1. ПЕРЕБОР ПАРОЛЕЙ (Brute Force)
   └─ Атакующий пытается угадать пароль перебором

2. ФИШИНГ (Phishing)
   └─ Отправка поддельных писем для получения учетных данных

3. УТЕЧКА ДАННЫХ
   └─ Компрометация базы данных учетных записей

4. ПОВТОРНОЕ ИСПОЛЬЗОВАНИЕ ПАРОЛЕЙ
   └─ Взлом одного сервиса дает доступ к другим

5. СЛАБЫЕ ПАРОЛИ
   └─ Использование простых паролей (123456, password)

6. СОЦИАЛЬНАЯ ИНЖЕНЕРИЯ
   └─ Манипуляция людьми для получения доступа

7. МАЛЬВЕР (Malware)
   └─ Программное обеспечение для перехвата паролей

8. УТЕЧКА СЕССИЙ (Session Hijacking)
   └─ Перехват токена сессии
```

### Меры защиты и лучшие практики

#### 1. Политики управления паролями

```
✓ ТРЕБОВАНИЯ К ПАРОЛЮ:
  • Минимальная длина: 12-16 символов
  • Обязательные символы: ПРОПИСНЫЕ, строчные, цифры, спецсимволы
  • Срок действия: изменение каждые 90 дней
  • История: не повторять последние 5 паролей
  • Сложность: не использовать имя, дату рождения, логин

✗ СЛАБЫЕ ПАРОЛИ (запретить):
  • Простые последовательности: 123456, abcdef
  • Словарные слова: password, letmein
  • Информация из профиля: имя, дата рождения
  • Повторяющиеся символы: aaaabbbb, 1111

Пример ХОРОШЕГО пароля:
  MyPass$2025!Dec#Secure
  ├─ Длина: 22 символа
  ├─ ПРОПИСНЫЕ: M, P, D, S
  ├─ Строчные: yass, ec, ure
  ├─ Цифры: 2025
  └─ Спецсимволы: $, !, #
```

#### 2. Многофакторная аутентификация (MFA)

```
ТРИ КАТЕГОРИИ ФАКТОРОВ:

Категория 1: "Что ты ЗНАЕШЬ?" (Knowledge)
├─ Пароль
├─ PIN-код
├─ Ответ на секретный вопрос
└─ Паттерн на экране

Категория 2: "Что ты ИМЕЕШЬ?" (Possession)
├─ Мобильный телефон (SMS, app)
├─ Аппаратный токен
├─ Смарт-карта
├─ USB-ключ
└─ Электронный сертификат

Категория 3: "КТО ТЫ?" (Inherence - Биометрия)
├─ Отпечаток пальца
├─ Распознавание лица
├─ Сканирование сетчатки
├─ Анализ голоса
└─ Динамика подписи

РЕКОМЕНДАЦИЯ: Использовать факторы из РАЗНЫХ категорий!
Хорошо: Пароль + SMS (знание + владение)
Плохо: Пароль + секретный вопрос (только знание)
```

#### 3. Управление привилегиями (Least Privilege)

```
ПРИНЦИП НАИМЕНЬШИХ ПРИВИЛЕГИЙ (PoLP):

Каждый пользователь должен иметь МИНИМУМ разрешений,
необходимых для выполнения своих задач.

ПРИМЕР ПРАВИЛЬНОГО РАСПРЕДЕЛЕНИЯ:

Уборщик офиса:
├─ Доступ к: коридорам, туалетам, складам
└─ НЕ имеет доступ к: серверным комнатам, офисам, базам данных

Администратор сервера:
├─ Доступ к: управлению системой, логам, сертификатам
└─ НЕ имеет доступ к: финансовым данным, личным документам

Финансист:
├─ Доступ к: финансовой системе, счетам
└─ НЕ имеет доступ к: кодовой базе, серверам, личным документам

НЕПРАВИЛЬНОЕ РАСПРЕДЕЛЕНИЕ (избыток привилегий):
Новый сотрудник получает одинаковые права со всеми администраторами ✗
```

#### 4. Аудит и мониторинг

```
СИСТЕМА МОНИТОРИНГА ДОЛЖНА ОТСЛЕЖИВАТЬ:

├─ Попытки входа
│  ├─ Время входа
│  ├─ IP-адрес
│  ├─ Устройство
│  ├─ Успешные входы
│  └─ Неудачные попытки
│
├─ Действия пользователей
│  ├─ Доступ к файлам
│  ├─ Изменение прав доступа
│  ├─ Удаление данных
│  └─ Экспорт информации
│
├─ Управление учетными записями
│  ├─ Создание новых учетных записей
│  ├─ Удаление учетных записей
│  ├─ Изменение ролей
│  └─ Блокировка учетных записей
│
└─ Обнаружение аномалий
   ├─ Вход в необычное время
   ├─ Вход с неизвестного устройства
   ├─ Попытка входа с подозрительного IP
   ├─ Множественные неудачные попытки входа
   └─ Необычно высокое использование привилегий

ОПОВЕЩЕНИЯ:
⚠ 5+ неудачных попыток входа подряд → Блокировка на 30 минут
⚠ Доступ к финансовым данным из другого IP → Требуется подтверждение
⚠ Удаление большого объема данных → Сведение администратору
⚠ Смена пароля у администратора → Логирование и уведомление
```

## Заключение

Система идентификации пользователя – это комплексная система, которая обеспечивает:

1. **Безопасность** – защита от несанкционированного доступа
2. **Управление доступом** – контроль прав пользователей
3. **Аудит** – отслеживание действий и активности
4. **Масштабируемость** – работа с тысячами пользователей
5. **Соответствие требованиям** – выполнение стандартов и регуляций

Успешная реализация системы управления идентификацией требует:
- Четких политик безопасности
- Технических контролей (шифрование, аутентификация)
- Регулярного мониторинга и аудита
- Обучения пользователей правилам безопасности
- Постоянного обновления и совершенствования системы
